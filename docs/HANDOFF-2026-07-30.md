## 1. The short version

The goal was to boot NORD TSS from disc instead of from a paper-tape image.
That is **not achieved**, but the reason is now known exactly rather than
guessed, and four real defects were fixed on the way.

The emulator can now boot from the cartridge disc, and it now runs the
NORD-1 `IOT` instruction correctly, which the archived bootstrap needs. The
bootstrap gets 50 pages into a 64-page reload and then destroys itself,
for a reason that is measured and understood (section 4).

## 3. What changed in nd100x

Five commits on `feat/prog-loader-and-shell-exec`, **not pushed**.

| commit | what |
|---|---|
| `7f9a3df` | `--boot=cdc`: boot from the cartridge disc. One 256-word sector from sector 0 into core, start at address 0 — what the LOAD button does on real hardware. Also fixes `boot_type_str`, which was missing `"prog"` and so mislabelled every entry from `BOOT_FLOPPY` on |
| `6a900b6` | **NORD-1 `IOT`**. `IOT` and `IOX` were dispatched identically. They are different instructions: `IOX` takes a flat register address in bits 0-10, `IOT` takes a device number in bits 0-7 and a function in bits 8-10 (`ACT`/`SKA`/`PIN`, all zero = `SNI`). `SKA` skips the next instruction when the device is ready, which the wait loop `IOT SKA DVN / JMP *-1` needs. Added a per-device hook; devices that do not claim a NORD-1 number keep the old behaviour |
| `bc84c47` | the disassembler decodes the function bits (`IOT SKA 144`, was `IOT 1144`); NORD-1 `LMR` mapped to the word-count register |
| `a6155c7` | `ND100X_CDC_TRACE=1` prints every disc transfer |
| `0de8e94` | only `PIN` arms interrupts, not `ACT` — the manual is explicit |

Evidence for the `IOT` change: ND-06.008.01 lists "IOT: NORD-1 compatible
Input/Output" beside `IOX` as separate privileged instructions, and the
NORD-10-S microprogram decodes `IOX`, `IOT` and `IDENT` separately with
`IOT` on its own microaddress. The function-bit meanings are from the
NORD-1 Reference Manual section 3.7.

**Verified no regression:** a normal tape-image boot still reaches `@ENTER`,
logs in as `SYSTEM` and runs `DATE`.

## 4. The `LOAD-SYSTEM` investigation — where it actually stands

### What works, each measured

| step | evidence |
|---|---|
| `LOADV` reads disc page 0 into core 0 | `core[0..7]` reads back the words written to sector 0 |
| `RCLR DP` executes it | `P=6`, `T=2`, `X=030424`, `L=3` — exactly `DKRST`'s first three instructions |
| `RDKOP` drives the disc | previously stopped dead on its first instruction; now transfers |
| the disc itself | `ND100X_CDC_TRACE`: 363 transfers in a run, **none out of range** |
| `DBOOT` reloads core | a marker written to core `1000` is replaced by that address's original contents |

### What fails, and why

`DBOOT` calls `RDKOP` **exactly 50 times** and then execution leaves it and
never returns. `INIT` (location 301) is never reached, so the machine keeps
paging and interrupts switched off — `STS=010044`, with `PONI` and `IONI`
clear, against `150100` with both set on a healthy system. That is why the
console is silent and why the disc address `XDISK` reads is rubbish.

The cause: **the bootstrap is not part of the system image it reloads.**

- `DKRST`/`RDKOP`/`DBOOT` were assembled by the `NMACF+TSBIN` build.
- The system image saved on the disc is the `MACF+DRUM+N10` build.
- Comparing the two builds word by word at `030416`-`030526`: **0 of 73
  words match.**
- `DBOOT` reloads 256 words per pass from core 0 upward. Pass 50 covers core
  `030400`-`030777`, which contains `RDKOP` (`030424`) and `DBOOT`
  (`030504`). At that pass it overwrites the instructions it is executing
  with unrelated code, and falls into whatever that code is.

The arithmetic, the 50-call count and the register dumps all agree.

Breakpoints in nd100x are a program-counter compare, not a memory patch, so
the 50-call cutoff is real execution and not a breakpoint lost to the
overwrite.

### Why the original worked

The bootstrap is **part of the system image**. The CDBIN tape loads the whole
system with `8CADR/0 8DKA/-1 8NWD/BLUES+1`, and that image contains
`DKRST`/`RDKOP`/`DBOOT` at those addresses because it is the same assembly.
When `DBOOT` later reloads core from disc, the words it writes over itself
are identical to what is executing, so the overwrite does nothing and the
loop continues. Our version breaks that: we put a boot sector from one build
onto a disc holding a different build.

### What a real fix needs

The disc image and the boot sector must come from **one assembly**. That
means building TSS as `NMACF+TSBIN` and bringing the system up from that
image, not patching sectors of an existing `MACF` disc. `DISC` is only
defined in the `NN10` branch, so that is the NORD-1 variant — now runnable,
because `IOT` works.

The obstacle: under `NMACF`, `OVERX` uses `)SOVER`/`)8DUMP` instead of
`)9MOVE`, and `mac` treats both as no-ops, so no overlay image gets written.
Solve that first or the system will not boot at all.

### Open question — do not skip this

Even in a consistent build, `DBOOT` reloads its own loop counters `DBCOR`
and `DBDKA` (about `030524`, inside the same page). Resetting `DBCOR`
mid-loop should restart or truncate the reload. Three explanations are
possible — the saved image holds a finished `DBCOR`, `BLUES` falls below
that page so the loop ends first, or the original layout placed the
bootstrap elsewhere — and **there is evidence for none of them**. Settle it
before claiming a working path.

## 5. Things that were believed and turned out wrong

Recorded because each cost a measurement, and because the pattern matters
more than the individual errors.

| claim | how it died |
|---|---|
| the disc address is illegal because it is negative | `DKADR` masks with `AND (17777` first; it computes to a legal cylinder |
| the disc image is too small | grew it to 16 MB, no change; the trace shows no out-of-range transfer |
| `--mms=1` breaks the tape-image boot | it does not; the empty consoles were a launch race between emulator starts |
| 32-bit vs 48-bit floating point explains the clock | the NORD-10/S manual settles it: the 32-bit option replaces six instructions and `LDF`/`STF` are not among them |
| the archived listings hold the original instruction words | they hold none; an address-column search returns zero on all six files |

Every one of these was reasoning that sounded right and was not checked
first. The ones that held up were single-variable experiments on a running
machine.

## 6. How to reproduce the current state

```bash
make build            # assembler + 718 tests + TSS, DRUM, MINIT artifacts
make clean-bringup
make auto             # MINIT format + cold start, needs nd100x
make verify           # free tracks + SYSTEM present
```

The probe scripts used for this investigation are in the session scratchpad,
not the repo. The useful ones to rebuild if needed: drive a login over the
debugger, send a command, then sample the program counter, read memory, and
set breakpoints on `DBOOT` (`030504`) and `RDKOP` (`030424`) to count reload
passes. `ND100X_CDC_TRACE=1` shows every disc transfer with its sector, core
address and word count.
